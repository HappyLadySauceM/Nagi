# Nagi v2.0 架构与产品体验优化评审

评审基线：`main` 分支 · `76a3a0a` · 2026 年 10 月 24 日

我已经重新读取了 Nagi 的最新代码，并对照你提供的 9 张后台截图进行评审。你提出的几个调整方向，大部分我都赞同，但有些地方建议采用比直接删除旧设计更稳妥的方式。

## 一、先说核心结论

Nagi 下一阶段不应该只是优化管理后台的外观，而应该从“单账号机器人管理工具”升级成“支持多身份、统一 Agent、短期上下文与长期学习的智能体平台”。

目前最大的问题不是技术栈落后，而是产品模型还没有完全统一。

| 评审维度     | 当前情况             | 优化方向                       | 优先级 |
| -------- | ---------------- | -------------------------- | --- |
| 多 QQ 账号  | 单连接、单运行时实例       | 多账号独立连接、统一管理               | P0  |
| 联系人/群聊   | 两个独立页面           | 合并联系人，Tab 切换好友/群聊          | P0  |
| 后台视觉     | 暗色表格卡片式管理后台      | 更有层次的 Agent Control Center | P1  |
| 工具白名单    | 已有配置字段，实际工具能力有限  | 改为 Agent 工具能力与权限模型         | P2  |
| 会话上下文    | 已有消息持久化及近期上下文    | 明确上下文窗口、保留策略和会话画像          | P1  |
| 长期记忆     | 按全局/群/个人/会话可见性区分 | 统一 Agent 知识，独立会话画像         | P1  |
| Agent 引擎 | 当前是自定义 LLM 回复流程  | 引入 Eino Agent Runtime      | P2  |
| 自我进化     | 缺乏完整反馈学习闭环       | 借鉴 Hermes 的记忆与经验沉淀         | P3  |

这里有三个需要首先确认的代码事实：

第一，Nagi 当前确实是单账号运行架构。 在 `cmd/app/assembly/work.go` 里只创建一个 `Transport`、一个 `ClientService`、一个 `Dispatcher`。虽然数据库部分表已经包含 `bot_id`，但这不等于多个 QQ 账号能同时在线、独立发送消息。

第二，SnowLuma 本身支持多账号。 官方文档明确说明每个 QQ UIN 可以拥有独立 OneBot 实例和网络配置。Nagi 需要改造的是如何发现、连接并管理这些实例，而不是重新实现 QQ 多账号登录。

第三，当前 Nagi 尚未真正使用 Eino。 我检查了 `go.mod` 和 `internal/agent/` 的代码结构，现有实现是自定义 OpenAI 兼容 API 调用与回复流水线。你提到的 Eino 工具调用还属于下一阶段的架构升级。

## 二、多账号：当前最值得优先解决的架构问题

### 2.1 SnowLuma 多账号是如何工作的？

SnowLuma 的设计是每个 QQ 账号独立拥有自己的 OneBot 实例。其配置可以采用：

```
SnowLuma
├── QQ 账号 A (10001)
│   └── OneBot WS :3001
├── QQ 账号 B (10002)
│   └── OneBot WS :3002
└── QQ 账号 C (10003)
    └── OneBot WS :3003
```

上面的端口是示例。官方说明第二个账号通常需要配置不同的监听端口，或者用反向 WebSocket 连接不同的接入端点，不能让所有实例争用同一个默认端口。

[image](https://www.google.com/s2/favicons?domain=https://snowluma.github.io\&sz=32)

snowluma.github.io

+1



Nagi 不应该只从一个 WebSocket 收到 `self_id`，就认为已经发现了整个 SnowLuma 中的所有账号。

### 2.2 推荐增加 AccountManager

SnowLuma — 多个 OneBot 实例

QQ A

QQ B

QQ C

AccountManager

账号注册表 · 连接生命周期 · 账号身份验证 · 状态聚合

共享 Agent

Eino · Memory · Skills

隔离业务状态

Scope · Conversation · Queue

建议第一阶段使用显式配置多个 SnowLuma 端点，而不是马上开发自动发现协议。

启动时连接每个端点，调用 `get_login_info` 获得账号身份，并与配置的预期 QQ 号校验。匹配成功后才允许对应的消息和动作进入业务流水线；账号不一致应隔离连接并告警，绝不能把上一账号的缓存绑定给新账号。

```
accounts:
  - id: main-qq
    qq: 10001
    endpoint: ws://127.0.0.1:3001
    token-env: NAGI_ONEBOT_TOKEN_A

  - id: second-qq
    qq: 10002
    endpoint: ws://127.0.0.1:3002
    token-env: NAGI_ONEBOT_TOKEN_B
```

这是建议的新配置格式，不是仓库当前已支持的 YAML。

后续可增加 SnowLuma 账号发现适配器，但需要先核实该版本是否提供稳定、带鉴权的账户列表接口，不应该依赖猜测的 WebUI 内部 API。

### 2.3 是否每个账号都创建一个 Agent？

我建议第一版不要。

采用：

- 多个 QQ 账号，各自连接、联系人、群聊与作用域独立；
- 统一 Agent 人格、通用能力、工具注册和长期知识；
- 每个账号及会话分别维护上下文、限流、投递状态；
- 后续如确有需求，再支持不同 QQ 账号绑定不同 Agent Profile。

这样符合你希望机器人拥有跨群、跨私聊共享知识的目标，而且避免多个 QQ 账号产生相互矛盾的长期记忆。

还有一个容易忽略的边界：如果两个机器人 QQ 号都在同一个群中，要避免两个账号同时响应同一段讨论。可为群会话设置一个默认主要参与账号，其他账号默认不主动插话。

### 2.4 现有代码怎么改

| 文件/模块                      | 具体改造                            |
| -------------------------- | ------------------------------- |
| `pkg/config/config.go`     | 单个 OneBot 连接配置改为账号列表            |
| `cmd/app/assembly/work.go` | 按账号创建运行时，并由 AccountManager 统一管理 |
| `internal/onebot/`         | 复用原有传输和协议实现，不重写 WebSocket       |
| `internal/directory/`      | 所有查询与同步显式传入 `bot_id`            |
| `internal/agent/`          | 发消息时根据 `bot_id` 路由到对应连接         |
| `cmd/app/routes/`          | 提供多账号列表、连接状态和账号级查询接口            |

数据库方面值得保留的是已有的 `bot_accounts` 和复合键设计。

但代码目前存在一个明显的多账号演进问题：`directory` 的列表查询接口没有要求 `bot_id`，`GroupMembers` 主要按 `group_id` 查询；`Scope` 的读取则通过当前唯一 `ClientService` 获取机器人 ID。

如果只是前端增加一个账号切换器，UI 切换了，数据却可能混用。所以必须先解决后端数据查询和执行链路的账号路由。

## 四、工具白名单：当前确实设计得有些超前

你问得很对：如果工具是写在 Eino Agent 中的，为什么还需要用户在页面上手动填一个工具名称？

我核对了实际代码，这里需要纠正一个产品层面的误导。

### 4.1 当前代码的真实状态

| 能力                           | 实际状态              |
| ---------------------------- | ----------------- |
| `scope_policies.tool_policy` | 已在 PostgreSQL 中定义 |
| 工具白名单编辑器                     | 已在 Web 页面实现       |
| Eino `ToolsNode`             | 尚未接入              |
| Nagi Agent Tool Registry    | 尚未实现              |
| 根据 `tool_policy` 过滤工具调用      | 未发现实际执行链路         |
| MCP 工具接入                     | 尚未实现              |
| Skills 系统                    | 尚未实现              |

也就是说，目前这个“工具白名单”主要是预留配置，不是一套已经生效的工具授权功能。

更关键的是，页面上提示“未授权任何工具，因此模型只能对话”，容易让管理员误以为只要在输入框填上 `search`，机器人就具备了联网搜索能力。

实际上并不是这样。

### 4.2 Eino 负责什么，权限系统负责什么？

Eino 的工具分为定义、注册、执行等环节。官方支持本地工具和 MCP 工具，`ToolsNode` 执行工具，ADK 的 `ChatModelAgent` 可以管理 Agent 推理与工具调用循环。

[image](https://www.google.com/s2/favicons?domain=https://www.cloudwego.io\&sz=32)

CloudWeGo

+1



工具在代码里定义，只代表这个能力存在，并不代表任意会话都应该有权调用它。

例如：

| 工具      | 私聊  | 普通群 | 管理群      |
| ------- | --- | --- | -------- |
| 查询天气    | 允许  | 允许  | 允许       |
| 查询公开资料  | 允许  | 允许  | 允许       |
| 发送群消息   | 按场景 | 允许  | 允许       |
| 禁言群成员   | 不适用 | 禁止  | 授权后允许    |
| 修改机器人设置 | 禁止  | 禁止  | 管理员确认后允许 |

这就是权限层仍然有价值的原因。它不能由 Eino 自己根据自然语言来决定。

建议采用：

`实际可用工具 = 已注册工具 ∩ Agent 启用能力 ∩ 当前账号权限 ∩ 当前会话权限`

并且在真正执行工具时再次检查授权，而不只是对模型隐藏工具列表。

### 4.3 现在怎么处理工具白名单？

我建议当前版本先从作用域编辑界面隐藏“工具白名单”配置。

等 Eino Tool Registry 真正完成后，再把这部分升级成一个更友好的“Agent 能力”界面，而不是让管理员手动填写字符串。

比如：

Agent 能力

未来版本设计

公开信息查询

查询资料、天气等公共信息

QQ 消息能力

发送回复、引用消息等普通动作

群管理能力

禁言、踢人等高权限操作

示意交互，不会修改真实授权。未来页面应从已注册工具清单读取能力，而不是手动填写。

Skill 也不应该与 Tool 混成一类。

Tool 是执行能力，Skill 是指导 Agent 如何完成一类任务的可复用流程。 未来加入 MCP 和 Skills 时，可以让 Skills 引用已注册工具，但不能通过 Skill 绕过工具权限。

## 五、记忆系统：建议重新定义，而不是继续细分可见性

这是我认为你这次提出的最有价值的调整。

你希望机器人在一个游戏群中慢慢了解到“这里主要讨论游戏”，并在以后进入其他游戏群时也能表现得更自然。

这里其实包含两类不同知识：

1. 这个群本身是什么样的群。
2. 机器人从游戏相关交流中学到了哪些跨场景有价值的知识。

第一类属于会话画像，第二类才属于长期记忆。

我建议正式把这两者拆开，而不是都放在 `memories` 表中再用可见性区分。

### 5.1 推荐的新记忆模型

QQ 消息 / Agent 交互

Conversation Context

短期上下文

最近消息、对话轮次、当前讨论主题

Conversation Profile

持久化会话画像

群类型、兴趣标签、聊天风格、互动习惯

Agent Long-Term Knowledge

跨账号 / 跨会话可复用的经过筛选的事实、知识和经验

Procedural Skills

反复验证有效的操作流程与经验方法，按需加载

### 5.2 短期上下文不应该叫长期记忆

我同意你不再保留原先所谓“会话级长期记忆”的方向。

短期上下文建议支持两个维度共同控制：最近 N 条消息，以及当前活跃讨论的时间范围。例如初始配置可以使用最近 20～40 条相关消息，并限制跨越太久的历史。最终应该按 Token 预算、活跃线程和聊天密度调节。

注意“上下文失效”不等于必须删除原始消息。原始消息是否留存，仍由作用域的数据保留策略决定。短期上下文可以失效，已获授权的消息记录则可继续用于人工排查或有限历史检索。

当前 `conversations` 表已存在 `summary` 字段，`active_threads` 也已经存在，但不能据此认为完整的上下文压缩、话题识别与长期学习已经实现。

### 5.3 会话画像：单独持久化

建议新增 `conversation_profiles`，而不是在 `memories` 里继续增加 `group`、`private_user`、`conversation` 等长期记忆类别。

一个群聊画像可能是：

```
{
  "conversation_type": "group",
  "categories": [
    {"name": "游戏", "confidence": 0.94},
    {"name": "二次元", "confidence": 0.72}
  ],
  "topics": ["Minecraft", "联机游戏"],
  "interaction_style": "轻松、熟人化、少量玩梗",
  "preferred_reply_style": "简洁、轻松",
  "evidence_count": 36,
  "source": "agent_observation",
  "status": "proposed"
}
```

这只是目标数据结构示例。

实现上建议采用渐进形成，而不是一条消息就确定群类型。

例如：

- 第一次观察到 Minecraft：记录一个弱信号，不修改群画像。
- 多次观察到游戏讨论：候选分类“游戏”，积累证据。
- 不同时间段持续验证：提高置信度，允许发布画像。
- 后来群聊主题改变：逐步降低旧分类权重，提出修订。
- 管理员手动设置分类：锁定对应字段，自动学习不能直接覆盖。

分类可以是多标签，而不是一个群只能属于“游戏群”或“学习群”。

用户画像同样可以有，但第一版只建议存储明确、非敏感、与当前交互有关的偏好，不要自动分析私人身份、敏感属性或群成员关系。

### 5.4 真正的长期记忆应该存什么？

我推荐把可跨会话复用的长期知识分为三种：

| 类别         | 示例                   | 是否适合全局    |
| ---------- | -------------------- | --------- |
| Agent 自身知识 | 自己支持哪些功能、如何回复特定类型问题  | 是         |
| 经验证的通用知识   | 某款游戏的公开玩法、工具的已验证使用经验 | 是         |
| Agent 交互经验 | 某类回答太长、某类插话经常不合适     | 经汇总、验证后可以 |

而某个群成员的私事、私人偏好、私聊内容，即使对 Agent 有帮助，也不应该自动进入全局知识。

这里必须保留来源、授权范围与隐私审查：跨会话复用的是安全、通用、可验证的知识，而不是把所有会话信息汇总成一个人人可见的超级聊天记录。

### 5.5 Hermes Agent 值得参考什么？

Hermes Agent 的核心并不是无限扩大 Memory，而是区分精选的持久记忆、可搜索的历史会话、可重用的 Skills，并通过反馈持续修订。其官方文档也强调短小、精选的长期记忆与按需检索的历史会话用途不同。

[image](https://www.google.com/s2/favicons?domain=https://hermes-agent.nousresearch.com\&sz=32)

Hermes Agent

+2



我建议 Nagi 学习这个机制：

Agent Learning Loop

从真实交互中形成可控的经验积累

交互完成 / 多次反馈

提取可复用的事实或经验

去重、冲突检查、隐私检查、验证

审批 / 自动低风险发布

持久知识 / 会话画像 / Skill

后续使用效果通过 Langfuse 反馈，决定保留、修订或撤销

这里不建议一开始就允许 Agent 自己修改全局 Prompt 或自动创建能执行危险动作的 Skill。

应该先做：

- 自动提议：允许 Agent 从授权对话中生成候选记忆或画像修改。
- 人工审查：涉及跨会话共享、敏感内容、Agent 行为规则或工具调用的修改，需要审批。
- 效果验证：通过回归样本确认没有降低回复质量或增加误回复。
- 版本回滚：任何已发布的 Agent 知识与 Skill 都应保留历史版本。

真正的进化不是“记得越来越多”，而是从交互中提炼更准确、更少、更有用的规则和知识，并且能够纠错。

## 六、界面评审：为什么现在看起来单调？

从你提供的截图看，当前界面并不是做得差，而是太像展示数据库状态的内部管理系统，缺少产品自身的个性和更有价值的交互入口。

我认为主要有五个问题。

### 6.1 信息密度与空间分配不合理

截图中有三个明显特征：

- 在较宽的桌面上，主要内容集中在中央，下面和两侧留白很大。
- 很多文字只有 10～12px 左右，状态说明和次要文本不易阅读。
- 卡片高度、间距及强调程度比较平均，没有形成明显的信息层级。

代码上也能找到对应原因：`sidebar.tsx` 使用 `text-[13px]`、`text-[10px]`，一些页面使用 `text-[11px]`，而 `globals.css` 的深色背景和卡片颜色比较接近。

建议把大多数正文调整到 14px，辅助说明 12～13px，页面标题 24～28px。不要只通过加大字号解决，而是同时调整卡片间距、表格行高和内容最大宽度。

### 6.2 概览页面缺少真正的 Agent 视角

现在的概览是：

消息数量、意图数量、任务状态、长期记忆状态、运行状态。

这些数据有用，但它们回答的是“程序运行情况”，不是管理员最关心的：

- 机器人现在在哪些群里活跃？
- 最近为何决定回复或沉默？
- 哪个 QQ 账号有连接异常？
- Agent 最近学到了什么？
- 哪个作用域需要人工处理？

建议重新设计成四个区域。

Agent Workspace

建议的新概览信息布局

设计草图

账号状态

连接与业务摘要

会话活跃

连接与业务摘要

### 6.3 导航层级需要重组

建议新的顶层导航是：

| 顶层导航  | 内容                       |
| ----- | ------------------------ |
| 概览    | 运行状态、活跃会话、待办             |
| 联系人   | 好友/群聊切换、详情、会话策略          |
| 会话    | 会话列表、历史、上下文窗口            |
| Agent | 模型、人格、工具能力及 Skills       |
| 知识与记忆 | 全局记忆、候选审批、学习历史           |

当前“作用域策略”可以继续保留内部路由，但普通用户最常用的策略入口应该是联系人详情页，而不是先进入策略列表，再通过 QQ 号查找。

### 6.4 要给界面加入内容感，而非一味发光

我建议继续保留现在的暗色 + 蓝紫色设计语言，不需要推倒重写。

优先增加有价值的内容元素：QQ 头像、群头像、成员缩略图、会话标签、带时间的动态记录、Jev 决策说明、Agent 操作状态等。

Magic UI 的动效可以保留在主统计卡片和连接状态，Motion 用在页面过渡、详情展开等位置。不要让所有表格行、边框和按钮持续发光。

### 6.5 当前缺少几个核心可操作页面

会话浏览器、会话画像、Agent 配置、学习历史是下一阶段最值得做的四个页面。

尤其是会话浏览器：如果管理员可以看到某条消息为什么没回复、当时用了哪些上下文、检索到哪些知识，再结合 Langfuse Trace，就能真正排查机器人行为，而不仅是看到 `not_addressed` 这样的统计标签。

这些页面应当在后端权限检查完成后再提供真实数据，避免未授权历史被 Web 页面查询到。

## 七、优化建议实践操作指南 v2.0

下面这份执行计划可以作为新一轮开发的任务基准。建议每个阶段单独提交、单独验收，不要让 Coding Agent 一次完成所有改造。

# Nagi v2.0 优化实施指南

**代码基线：** `HappyLadySauceM/Nagi` — `main` — `76a3a0a`

**总体目标：** 将现有 Nagi 升级为支持多 QQ 账号、统一联系人管理、会话画像、跨会话知识记忆，以及基于 Eino 的可扩展 Agent 平台。

**实施原则：**

- 保留现有 SnowLuma / OneBot 11 通信能力。
- 不重写已有 Jev 意图判断与消息持久化流水线。
- 所有账号及会话操作必须显式绑定身份。
- 只在必要时改动对应模块，不能附带无关重构。
- 数据库迁移必须遵守仓库 `AGENTS.md` 及数据库迁移规范。

## P0 — 多账号运行时与数据隔离

**目标：** Nagi 能够同时接入两个或更多 SnowLuma OneBot 实例，并正确识别消息来源、路由发送动作。

### 后端任务

- 为配置结构引入账号连接列表，每个连接配置预期 QQ UIN、WebSocket endpoint 与凭据引用。
- 新增 AccountManager，负责连接初始化、连接身份核验、重连状态、停止及账号注销。
- 将现有 Transport / ClientService / Dispatcher 按账号独立实例化。
- 保留共享的业务服务与数据库连接池。
- Directory 查询显式按 `bot_id` 过滤；消除按“最近同步账号”隐式读取的逻辑。
- Scope、Conversation、Intent、Agent、Memory 的调用链明确携带账户身份。
- 消息发送时根据 `bot_id` 查找对应 OneBot Sender，账号离线时不得回退发送给其他账号。
- 管理 API 提供账号列表、账号连接状态、指定账号同步等功能。

建议新接口：

```
GET  /api/v1/accounts
GET  /api/v1/accounts/{bot_id}
POST /api/v1/accounts/{bot_id}/sync

GET  /api/v1/accounts/{bot_id}/contacts
GET  /api/v1/accounts/{bot_id}/groups
GET  /api/v1/accounts/{bot_id}/groups/{group_id}/members
```

### 必须验证

- 两个账号同时连接时，双方消息正常收发。
- 相同群 ID 在不同账号下不会导致目录或权限数据混淆。
- 同一账号两个不同连接被意外重复注册时能够识别冲突。
- 账号断线不会导致其他账号停止工作。
- 无法把发给账号 A 的消息通过账号 B 发送。
- 重启后各账号作用域和会话数据保持正确。

## P1 — 统一联系人与 UI/UX 优化

**目标：** 把好友、群聊统一为联系人工作区，优化页面的信息层级及浏览体验。

### 前端任务

- 将 `/contacts` 设计为包含“好友 / 群聊”Tabs 的统一页面。
- 保留好友列表与群列表独立业务组件，复用搜索、分页、空状态与详情面板。
- 将群成员页整合进群详情。
- 顶部提供账号切换器，展示账号头像、QQ 号及连接状态。
- 账号切换后，相关 Query Key 必须包含 `bot_id`，不可复用上一账号缓存。
- 为联系人增加可管理的业务标签或自定义分组。
- 支持从联系人详情直接进入作用域设置。
- 对超宽显示器优化内容布局，不再让页面只有一小块表格。
- 统一字号、间距、按钮尺寸、视觉层级及响应式布局。

### 建议修改范围

```
web/src/app/layout/
web/src/app/router.tsx
web/src/features/accounts/
web/src/features/directory/
web/src/features/scopes/
web/src/styles/globals.css
web/src/lib/api/
```

### 必须验证

- 好友和群聊切换不丢失搜索与当前账号身份。
- 账号切换时上一账号的资料不会短暂闪现为新账号的数据。
- 手机、平板、桌面界面都可正常操作。
- 暗色/亮色对比度和键盘操作符合基本可访问性要求。
- 不出现静态假数据冒充实时运行数据。

## P2 — 上下文与会话画像重构

**目标：** 区分短期上下文和持久化会话画像。

### 数据职责

`conversations`：保留会话身份、最后活动时间及必要的上下文状态。

`messages`：保留已授权的历史消息，受留存策略控制。

`conversation_profiles`（新增）：保留会话类型、主题、标签、氛围、回复偏好、证据和版本。

### 实施任务

- 为每个群聊或私聊建立统一的 Conversation Profile。
- 支持自动多标签分类，例如“游戏”“学习”“二次元”。
- 提供分类证据、置信度、最近验证时间。
- 管理员手动指定的画像字段支持锁定，防止自动学习覆盖。
- 近期上下文同时受条数、活跃时间和 Token 预算控制。
- 新增异步画像分析任务，不影响实时回复延迟。
- 画像更新必须有版本历史和撤销能力。
- 群画像仅在授权会话中生效，不自动公开其来源消息。

### 管理接口

```
GET   /api/v1/conversations
GET   /api/v1/conversations/{id}
GET   /api/v1/conversations/{id}/profile
PATCH /api/v1/conversations/{id}/profile
GET   /api/v1/conversations/{id}/profile/history
```

## P3 — 长期记忆与 Agent Learning

**目标：** 让真正跨会话有价值的知识进入长期记忆，而不是把每个群聊的所有特点都当作全局 Memory。

### 实施任务

- 将原有 memory visibility 模型中的会话特征逐步迁移到 Conversation Profile。
- 保留来源归属与访问控制，绝不直接把私聊内容升级为全局知识。
- 建立 Agent 级知识存储，支持候选、审核、激活、修订、失效和撤销。
- 引入 Memory Extraction：在交互后异步提取有价值的事实、反馈和经验。
- 实施去重、冲突识别、来源校验和隐私过滤。
- 维护紧凑的高优先级 Agent Memory，其他知识按需检索。
- 使用 Langfuse 评估引入记忆前后的回复质量。
- 提供学习历史页面，展示 Agent 学会了什么、为什么、来自何处及如何撤销。

### 数据迁移注意

不直接删除旧 `memories` 表或批量清空历史数据。先新增模型，完成分类迁移和业务切换，再以独立可回滚迁移清理不需要的字段。

## P4 — Eino Agent Runtime

**目标：** 用 Eino 承载 Agent 的模型调用、工具注册和执行循环，替换当前自定义的纯文本生成实现。

### 实施任务

- 保留 Jev + 规则的外部回复决策层。
- 将现有 `ReplyExecutor` 作为 Agent 接入边界，避免重写消息调度器。
- 引入 Eino ChatModelAgent 或与当前需求相符的 Agent 运行组件。
- 通过 Eino Tool / ToolsNode 注册基础能力。
- QQ 动作工具只依赖 `onebot/contracts` 中的最小能力接口。
- 增加模型调用次数、工具调用次数、执行时间和 Token 上限。
- 对危险工具配置明确的授权和确认机制。
- 工具执行前重新检查账号、会话和操作权限。
- 将 Agent 执行轨迹、模型调用和工具结果接入 Langfuse。

### 当前 UI 调整

在真实工具注册与授权层完成之前，从作用域编辑页面隐藏尚未生效的工具白名单编辑器。

Eino 接入完成后，再提供可勾选的 Agent 能力面板。

## P5 — MCP、Skills 与持续自我优化

**目标：** 让 Agent 可以使用新的能力，并从反复执行的成功经验中提炼工作流程。

- Tool Registry 统一管理内置工具与 MCP 工具。
- Skills Registry 管理按需加载的流程性知识。
- 每个 Skill 保留名称、用途、版本、来源和所需工具能力。
- Agent 可提出 Skill 创建或修订请求。
- Skill 发布前验证来源、权限、执行结果和风险。
- 支持管理员审核、禁用和版本回滚。
- 通过 Langfuse 记录执行成功率、错误率和学习效果。
- 首期禁止 Agent 无审核地修改自己的系统级指令或扩大工具权限。

## P6 — 管理后台产品化

**目标：** 从当前 CRUD 管理后台升级为 Agent Control Center。

### 页面

1. 概览：多账号连接、活跃会话、Agent 任务及待办。
2. 联系人：好友/群聊统一入口、标签与作用域配置。
3. 会话：消息浏览、上下文窗口、会话画像与回复决策。
4. Agent：人格、模型、工具能力与 Skills。
5. 知识与记忆：长期知识、候选审批、学习历史。
6. 运行监控：意图判断、Token 成本、错误与 Langfuse。
7. 设置：账号连接、安全、系统配置。

### 视觉要求

- 极简深色优先，同时保留高质量亮色主题。
- 正文阅读优先，避免过小字号。
- 动效只用于有意义的状态变化、过渡和反馈。
- 使用真实数据驱动指标。
- 展示清晰的错误状态、加载状态、空数据及操作结果。
- 移动端保持可操作性，不要求完全复制桌面布局。

## 实施与发布规范

每个阶段应单独提交，提供：

- 变更目的、范围与依赖关系。
- 真实修改的文件清单。
- 对外接口及数据库兼容说明。
- 必要的测试结果与未覆盖项。
- 失败回滚方案。

后端验证以仓库 `just verify` 和受影响并发测试为准。涉及数据库修改时，必须在隔离测试库执行迁移往返验证；不能指向开发或生产数据库。

前端应通过 `pnpm lint`、`pnpm typecheck`、`pnpm test`、`pnpm build`，并在浏览器完成关键交互验证。

**禁止：** 未经明确要求顺手重构无关代码、覆盖现有用户修改、修改工程约束以绕过测试、删除失败测试，或仅为了视觉展示添加没有真实能力的功能入口。

## 八、实际应该先做什么？

我会把接下来第一轮改造的范围控制为 P0 + P1：多账号正确性与联系人交互优化。

### 建议开发顺序

1. 先解决账号隔离

   先完成 AccountManager 和数据层显式 `bot_id`，用两个 SnowLuma 账号联调。
2. 合并联系人与群聊

   做好友/群聊 Tabs、账号选择器、联系人详情与作用域入口。
3. 再重新定义会话与记忆

   加入 Conversation Profile 和短期上下文策略，在此基础上建设学习机制。
4. 最后引入 Eino 与 Skills

   用稳定的 Tool Registry 和权限检查承载扩展，而不是先制作一堆功能设置项。

### 最后一个重要建议

你现在说的“长期记忆”，实际上更接近 Agent 的持续知识学习与能力进化系统。

我建议未来产品里也相应调整命名：

- “长期记忆”升级为 知识与记忆。
- “群聊/私聊记忆”改成 会话画像。
- “工具白名单”未来升级为 Agent 能力。
- “QQ 账号”从独立详情页升级为全局可切换的 连接账户。

这样不仅界面更自然，底层概念也一致。
