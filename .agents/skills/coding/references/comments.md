# 注释约束

## 何时添加注释

注释用于说明从代码本身难以看出的意图、必要约束、边界行为和设计取舍。优先让代码
自身表达清楚，不用注释替代清晰的命名和逻辑，也不为补注释顺手重构代码。

公开接口或行为不直观的函数需要必要的文档说明；简单赋值、显然的条件判断和
逐行翻译代码不需要注释。不要为每个函数机械添加固定模板。

## 语言与格式

- 新增或实质调整的代码注释采用英文在上、中文在下，两种语言表达相同的含义。
- 遵循目标语言的文档注释规范。Go 的声明文档以被说明的标识符开头，紧邻声明；
  不为参数和返回值机械添加不符合项目风格的标签或冗长区块。
- 双语段落按说明内容对应组织，保持简洁、易读，不复制两份不同含义的说明。
- 日志使用英文，日志消息不属于双语代码注释。

## 函数与接口说明

对确需说明的函数，描述功能、关键参数含义、返回值和错误语义；存在重要约束时，
说明副作用、并发使用限制、取消或超时行为，以及资源的持有和释放责任。

只有调用方式或边界容易误解时才增加使用示例，示例必须与当前接口一致。不要把
代码中已清楚表达的每个参数都重复展开，也不为补充示例新增测试文件或文档文件。

## 准确性与安全

- 注释必须符合当前实现。修改相关行为时，仅同步调整受影响的注释；删除相关实现时，
  移除随之失效的说明。
- 未核实的线程安全、性能、幂等性和兼容性不能写成保证；必要时先核实当前代码。
- 不写真实凭据、令牌、个人信息或其他敏感数据；示例使用明确的非敏感示例值。
- 注释说明当前逻辑为什么必须如此，不记录 Agent 的历史错误、用户纠正过程或
  与当前任务无关的未来 TODO。

## 改动边界

注释修改与撤销遵循 [防乱改约束](change-scope.md)。仅调整本次需求直接涉及的注释，
不把新增本约束理解为全仓库补注释、翻译旧注释或统一格式的授权。
