# 防乱改约束

## 任务模式

- 审查：读取、分析和必要的非修改验证，输出结论；不修改文件。用户明确要求修复后，
  才对授权问题进入开发模式。
- 开发：实现当前需求及其必要验证，不附带额外功能或无关改进。
- 撤销：只消除用户指定的修改并恢复对应行为，不借此增加新规则、实现或测试。

用户的纠正是当前任务的边界，不自动成为新的长期工程规范。任务中的状态查询或
澄清不取消原目标；用户明确取消或改变目标时，按最新要求调整。

## 修改前确定范围

检查当前工作区状态和相关代码，在对话或内部记录中确定任务目标、完成条件、必须
修改的文件及理由，以及不涉及的内容。不要额外创建范围清单或任务文档。

默认选择文件最少、代码最少、影响最小且容易审查的合理方案。简单任务通常控制在
1～3 个文件；这是检查范围膨胀的参考，不是阻止必要修改或明确授权重构的硬限制。

记录用户已有、未提交或并行修改，不将它们当成本次产生的差异。

## 实施边界

- 不顺手重构、重命名、重组目录、补功能、优化性能或修复其他 Bug。
- 不自行修改依赖、CI、部署配置、文档、日志、注释、无关测试或格式；只有当前明确
  需求直接涉及，或完成该需求确有必要时才能修改。
- 默认不新增文件。新增文件须说明不创建时为何无法合理完成当前任务；未来复用、
  更漂亮或预留扩展都不足以成为理由。
- 发现其他问题可简短报告，不自行修复。用户要求全局排查或系统重构时，按实际授权
  范围完成，不用最小改动原则拒绝必要工作。
- 新发现的必要修改先检查已有授权。仍在当前需求内的必要工作直接完成；只有真正
  增加目标、改变明确限制或需要额外授权时才询问，不反复确认已批准的方案。
- 普通开发任务不能修改本技能、AGENTS.md 或其他检查规则来放行自己的越界修改。
  只有用户明确要求维护这些规则时才修改。

## 撤销与失败方案

用户要求删除、撤销或恢复时，仅处理指定实现及其必要关联修改。不要留下解释历史
错误的注释、禁止规则、额外测试或文档。

失败方案先移除，再实施必要替代方案，不保留无用结构后继续叠加补救代码。若错误
由本次不必要改动造成，优先撤销该改动，而不是再加功能修补它。

撤销以属于本次任务的具体差异为依据。不要覆盖用户已有或并行修改，不使用整仓库
重置代替局部恢复；同一位置发生冲突且无法确定归属时，先澄清再处理。

## 最终范围检查与停止

检查 `git status --short`、暂存和未暂存的 diff、文件列表及统计，并检查本次新增的
未跟踪文件内容；Git diff 不会自动展示未跟踪文件。

逐个文件、逐块独立改动核实：它服务于哪项当前需求？如果恢复它，是否仍能满足
需求？后者为是且没有必要的验证或关联理由时，移除本次多余改动。

清除本次临时代码、调试代码、无关格式、注释、文档、测试、兼容逻辑及失败方案
残留；不删除用户原有内容或用新增代码掩盖问题。

需求已满足、必要验证通过、没有已知由本次修改引入的错误、最终差异只含必要改动
时立即停止。完成后不继续寻找可优化之处。
