# 数据库与迁移约束

## 迁移入口

- 进程启动是唯一迁移入口：连接成功后立即执行 `db.Migrate`，失败则退出，不带着旧 schema 继续服务。
- 不提供第二套手工迁移路径：不写迁移脚本、CLI 或 `just` recipe，不在脚本中散落 SQL。
- 不在运行期用临时 DDL 兜底（如 `CREATE TABLE IF NOT EXISTS`、`ALTER TABLE ... IF NOT EXISTS`）。

## 可回滚

- 每个版本必须成对存在 `NNNN_name.up.sql` 与 `NNNN_name.down.sql`；缺一即视为无效迁移。
- `down` 必须把结构还原到上一版本。涉及数据回填、搬迁或格式转换时，同时提供逆操作；确实不可逆时在迁移文件与提交说明中写明原因和恢复手段。
- 破坏性变更（`DROP`、`RENAME`、`TRUNCATE`、类型收窄、加非空列）单独成版本，可被独立回滚，并在提交说明中给出回滚命令。
- 新增非空列必须带默认值，或拆成"可空 → 回填 → 加约束"三步，保证回滚时数据不丢。
- 迁移保持幂等、单事务语义；执行期间不调用外部服务、不依赖网络。

## 数据安全

- 禁止手工改库"修复"问题；任何 schema 或数据缺陷都通过新增迁移解决。
- 集成测试的 `QQBOT_TEST_DSN` 只能指向独立测试库：迁移往返测试会删表，指向开发库或生产库等同于清空数据。
- 不在开发库或生产库执行 `db.Down`。

## 验证

- 修改 schema 后，在独立测试库运行迁移往返测试（`pkg/db` 下的集成测试）。
- 涉及数据回填时，用一组样例数据验证 `up → down → up` 后数据不丢失或可按说明恢复。
- 启动日志应能确认本次应用的迁移版本；没有日志证据时，不声称迁移已生效。
