# 编码架构约束

## 修改前分析

先读取受影响代码和调用方，确认模块职责、接口与输入输出、数据流、现有技术栈、
错误路径及实际风险，再确定实现方案。不要凭文件名或先前印象推断当前实现。

分析深度与任务复杂度匹配：简单数值修改确认使用位置和影响即可；新增功能或明确
授权的系统重构需说明模块划分、接口、数据流、技术选择和风险。分析使用对话或内部
记录，不因此创建架构文档。

## 设计与实现

- 优先沿用现有设计、语言规范、项目约定和依赖。只有用户明确要求或当前需求确实
  无法合理完成时，才改变模块边界、接口或技术栈。
- 在受影响范围内保持逻辑清楚，处理真实错误和相关边界；不为理论上的健壮性增加
  无关校验、fallback、配置项、抽象或 helper。
- 当前项目处于开发阶段，替换明确涉及的旧实现时不添加过渡兼容层；该原则不授权
  删除其他模块、接口或尚未涉及的实现。
- 必要的新抽象必须解决当前实际问题，不能仅以未来复用或扩展为理由。

## 并发与资源生命周期

任务涉及并发、外部访问或资源管理时，检查超时、context 取消、并发上限、共享状态、
阻塞路径、资源释放和错误传播。为需要并发处理的工作采用适合现有技术栈的非阻塞
方案，避免无界任务、泄漏或将请求无限排队。

本项目特有的生命周期检查点：Transport.Run 与 Dispatcher.Run 必须可被 ctx 取消；
事件通道的关闭路径唯一且有锁保护；管理 API goroutine 退出前完成优雅停机。

Go 的 goroutine、channel 和 context 应服务于实际生命周期与并发需求；不机械地
把带 context 的同步接口改成异步，也不为普通修改增加 goroutine。

性能优化须直接服务于本次需求或已确认的相关瓶颈，不顺手增加缓存或更换实现。

## 安全与表达

- 对受影响输入、输出、权限边界及外部访问检查实际安全风险。access token、完整
  消息体等敏感数据不进入公开错误或日志；管理 API 默认只监听本机，发现其他安全
  问题可报告，不自行扩展修复。
- 使用中文交流，日志使用英文；只修改本次涉及的日志，不统一整理整个文件。
- 代码注释遵循 [注释约束](comments.md)，只处理本次涉及的内容。
- Go 命令直接使用 `go`，不要通过环境变量或参数重设 `GOCACHE`。
