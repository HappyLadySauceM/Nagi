# review

## 目标

在功能修改进入 Git 提交流程前，用一次独立全量审查和真实运行验证确认用户需求已经实现。
复审只核对已经证实的修复，不把整份改动再审一遍。

审查通过不等于任务完成：涉及运行行为时必须实际执行功能，涉及前端展示时必须通过页面完成前后端联调。

## 适用判断

- 待提交或待推送内容改变运行行为、接口、数据处理、配置语义或页面功能时，按本技能执行。
- 只修改文档、注释或纯格式且不影响运行行为时，跳过审查循环和功能测试，仍做模块提交检查并提交。
- 混合提交中存在功能修改时，整个待提交功能范围均需审查和验证。
- 执行 Git 操作前先检查 `git status --short`、暂存与未暂存差异以及未跟踪文件内容，只处理当前任务范围，保留用户已有的其他修改。
- 无法区分本次改动与其他并行修改时，先暂停 Git 操作并澄清范围，不把未知内容纳入提交。

## 模块提交检查

一个功能模块的实现和必要验证完成后立即做这次检查，通过后才开始下一个模块。模块是一份能独立审查、独立回滚的用户可观察行为或一个独立修复。未提交差异里每多一个模块，全量审查就要多看一块互不相关的代码，遗漏和幻觉都会增加。

可以审查提交，须同时满足：

- 该模块的行为已经实现，这个模块自己的必要验证已经做完。
- 待提交差异只含这个模块，没有下一个模块、无关修改，也没有和用户已有改动缠在一起。
- 再改就会开始另一个可独立审查的行为。到这里就停，不为了「顺便」把下一个行为一起写完。

有一条不满足就先补齐或拆开，并说明缺什么。在此之前不开始下一个模块。用户明确说先不要提交时，只报告检查结果。

纯文档、注释或纯格式且不影响运行行为的模块，跳过审查循环和功能测试，按 git 技能提交。功能修改在检查通过后进入审查循环，审查和功能测试都通过才提交。

提交写到当前任务分支。还在 `main` 上时，先按 git 技能建分支再提交。push 和 PR 留到用户要求或任务收尾，不因为一次模块提交就推送。

## 审查循环

同一变更最多 3 轮，含第 1 轮全量审查。第 3 轮结束后仍有核实成立的必须修复项时，停止循环并向用户报告，不自动加轮，也不提交。用户明确要求继续后，才可以再开一轮增量复审。

每轮使用新的只读 subagent。主 agent 不代替 subagent 审查。

### 1. 全量与增量

- 第 1 轮是唯一的全量审查。subagent 只读本次待提交差异、这些差异的直接调用方，以及已有测试。
- 第 2 轮及以后是增量复审。subagent 只读上一轮必须修复项对应的修复差异，以及该差异直接碰到的调用方。
- 增量复审不重读整份改动，不复查本轮差异未触及的代码。
- 增量复审中，位于本轮差异之外的新问题直接丢弃。除非摘录能证明这次修复引入了用户可观察的错误。

### 2. 交给 subagent 的材料

提示词只含下列材料，不粘贴实现过程、对话原文或历史轮次全文：

- 用户需求，一两句话；
- 本轮允许阅读的路径范围；
- 增量复审时，上一轮每条必须修复项的一行处置：`已修 <file>`，或 `不成立 <一句代码依据>`。

处置清单只用于避免重复审理已关闭条目，不是对实现的背书。subagent 可以用与当前文件一致的新摘录推翻其中一条。

不提供实现辩护、预期结论或「其余都正确」。不要求 subagent 认可当前实现。不把 `.review/` 中其他变更的文件放进提示词。

subagent 只读源码和已有测试，不运行 `go test`、`pnpm test`、构建或服务。测试由主 agent 在功能测试阶段执行。

### 3. 输出契约

subagent 只按本契约输出。无必须修复项时，全文只有一行：

```text
无必须修复项
```

有必须修复项时，每条使用：

```text
- <file>:<line>
  摘录：<与该行一致的原文，不改写>
  行为：<用户可观察到的错误结果>
  修复：<最小改动，一句话>
```

必须修复只包括：用户可观察行为错误、数据损坏或丢失、越权、真实凭据泄露、接口契约破坏、本次改动引入的确定回归。

最多再附 3 条备注，每条一行，前缀 `备注：`。备注不触发修改，也不触发下一轮。

下列输出无效。主 agent 丢弃，不据此改代码，也不为此再开一轮：

- 没有摘录，或摘录与当前文件对不上；
- 只涉及风格、命名、注释或理论上的健壮性；
- 建议把本地配置改成环境变量，且不构成真实凭据泄露；
- 建议新增配置、抽象或无关重构；
- 复述架构、罗列「已核实无问题」，或粘贴测试日志。

### 4. 保存

每个变更只写 `.review/<change-slug>.md`。每轮把 subagent 原文和主 agent 的一行处置追加进去，不改写原文，不为每一轮另建文件。

`.review/` 只作本地临时记录，已被 `.gitignore` 忽略，不得暂存或提交。开始本次审查时，删除其中不属于当前变更的文件，避免过期结论进入后续上下文。

### 5. 核实与停止

- 逐条打开 `file:line`，核对摘录是不是原文，以及所述行为是否由这段代码和用户需求推出。对不上就作废。
- 只修复核实成立的必须修复项。不为备注改代码。
- 不成立的条目写下一条代码依据后关闭。已关闭且后续差异没有改到该处时，不得因复审再次提起而重新打开。
- 只有核实成立的必须修复项被改动后，才启动下一轮增量复审。
- 同一轮先核实再修改。不为了清掉清单连续改代码，然后整库重审。

## 本地功能测试

审查通过后必须执行功能测试，不能用审查结论、单元测试、构建成功或接口返回成功替代。

### 1. 自动化检查

- Go 改动执行 `just verify`（`go mod tidy`、`go vet ./...`、`go test ./...`、`go fmt ./...`）。
- 前端改动在 `web/` 下执行 `pnpm typecheck`、`pnpm lint`、`pnpm test`；影响构建、路由或产物时再执行 `pnpm build`。
- 涉及数据库或并发行为时，按改动影响追加相应集成测试或 `go test -race`。
- 检查失败先判定原因。由本次改动导致时修复，再按测试失败闭环做一轮增量复审，并重跑受影响的检查。

### 2. 启动真实环境

- 优先使用 `just run` 启动后端和前端；后端默认 `127.0.0.1:5080`，前端默认 `127.0.0.1:5173`。
- 缺少本地基础设施时按 README 使用 `just dev-init`，不得执行 `just dev-clean` 等会破坏数据的清理命令。
- `/livez`、`/readyz` 或前端可访问仅表示环境就绪，不能作为功能通过依据。
- 记录启动前已有的服务；测试结束后只停止本次启动且不再需要的进程，不干扰用户正在运行的环境。

### 3. 验证后端功能

纯后端或前端未涉及的改动，至少通过实际业务入口完成用户需求对应的流程：

- 验证真实输入、输出和状态转换，而不只检查 HTTP 状态码；
- 核对必要的数据持久化、重新读取结果、失败路径和日志；
- 涉及消息链路时，确认从入口到最终可观察结果的完整路径；
- 外部依赖不满足时明确标记未验证，不得用 mock、单元测试或接口空响应冒充真实功能通过。

### 4. 前后端联调

前端改动、后端改动影响页面行为，或需求包含页面展示时，必须启动前后端并通过真实页面验收：

- 使用当前环境可用的浏览器自动化能力打开对应页面，实际执行用户操作；没有浏览器能力时报告阻塞，不将接口验证视为通过。
- 覆盖目标模块入口、主要内容展示、核心操作、结果反馈和刷新后的状态。
- 检查相关加载、空数据、失败提示，以及浏览器控制台和网络请求中的异常。
- 将页面观察与后端数据、日志相互核对，确认不是只有接口返回成功或页面静态占位。
- 完整模块必须包含前端展示与交互；只调通接口、只断言 DOM 存在或只截取静态页面均不算通过。

### 5. 测试失败闭环

功能测试发现由本次改动导致的缺陷后：

1. 修复问题，并按 coding 技能的测试约束补充必要回归测试；
2. 对这次修复做一轮增量复审，只看该修复差异；
3. 重新执行自动化检查和受影响的功能流程，包括相关页面联调。

这一轮若再提出核实成立的必须修复项，不再自动继续。向用户报告剩余问题，不提交。不能沿用修复前的审查或测试结论。与目标功能无关的既有问题如实报告，不扩大修改范围。

## Git 提交门槛

只有同时满足以下条件才可执行 commit、push、创建 PR 或推送 PR 更新：

- 最后一轮审查的原文是 `无必须修复项`，或其余条目均已核实为不成立；
- 所有由审查或功能测试确认的问题均已修复并重新验证；
- 自动化检查、本地功能测试和适用页面联调均通过；
- 没有未说明的未验证项、已知功能回归或被隐藏的失败；
- 最终差异只含当前任务需要的修改，`.review/` 内容未进入暂存区。

审查、修复和测试针对的代码内容发生变化后，已有结论失效。失效后按增量复审处理，不把整份改动再审一遍。同一份未变化内容在 commit 后继续 push 或创建 PR 时，可以复用已通过的审查与测试结果。

## 收尾

完成本次要求的 commit、push 或 PR 推送后，删除对应的 `.review/<change-slug>.md`；目录为空时一并删除。Git 操作失败时保留该文件，便于继续处理。

最终汇报实际执行的审查轮次、每条必须修复项的处置、自动化检查、功能测试和页面联调结果，以及任何未能验证的内容。不复述 subagent 原文。
