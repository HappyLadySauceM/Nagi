# review

## 目标

在功能修改进入 Git 提交流程前，以独立审查和真实运行验证确认用户需求已经完整实现。审查通过不等于任务完成：涉及运行行为时必须实际执行功能，涉及前端展示时必须通过页面完成前后端联调。

## 适用判断

- 待提交或待推送内容改变运行行为、接口、数据处理、配置语义或页面功能时，按本技能执行。
- 只修改文档、注释或纯格式且不影响运行行为时，不触发本技能。
- 混合提交中存在功能修改时，整个待提交功能范围均需审查和验证。
- 执行 Git 操作前先检查 `git status --short`、暂存与未暂存差异以及未跟踪文件内容，只处理当前任务范围，保留用户已有的其他修改。
- 无法区分本次改动与其他并行修改时，先暂停 Git 操作并澄清范围，不把未知内容纳入提交。

## 审查循环

### 1. 启动独立审查

每轮启动新的只读 subagent 审查当前待提交代码。向 subagent 只提供以下信息：

- 本次功能更改及其对应用户需求；
- 需要检查的工作区范围，并要求其自行查看差异、相关实现和测试；
- 要求输出问题严重级别、依据和建议，不修改代码。

不得向 subagent 提供实现辩护、预期结论、已认定无问题的说明，或要求其认可当前实现。不得由主 agent 代替 subagent 完成本轮审查。

### 2. 审查重点与尺度

重点检查：

- 用户需求是否完整实现，用户可观察行为是否正确；
- 主流程、边界条件、失败路径、并发与状态变化是否正确；
- 数据读写、持久化、接口契约、权限和前后端联动是否一致；
- 是否引入回归、错误处理缺口、不可观测失败或不必要复杂度；
- 代码质量、可维护性以及必要测试是否与现有规范一致。

保持务实，不因非必要细节阻塞提交。例如仅建议将配置文件中的明文本地值改为环境变量，且不构成真实凭据泄露时，可以忽略。真实凭据、越权、数据损坏、用户可见功能错误和关键回归不属于小问题。

### 3. 保存审查建议

每轮审查结束后，将 subagent 的原始建议写入 `.review/<change-slug>-round-<N>.md`。记录严重级别、涉及文件或行为及判断依据，不改写为已修复事实。

`.review/` 仅用于本地临时记录，不得暂存或提交。该目录已被 `.gitignore` 忽略。

### 4. 核实、修复与复审

- 主 agent 逐项核实建议：检查代码事实、复现条件、相关测试和用户需求，不把建议直接当作结论。
- 对确认存在的问题进行修复；必要测试按 coding 技能的测试约束补充。
- 对不成立的建议不修改，并保留可复核的依据。
- 只要被审查代码发生变化，就重新启动一轮独立 subagent 审查，并保存新的建议文档。
- 循环直至没有必须修复的功能问题。低优先级、非必要建议不应造成无限复审。

## 本地功能测试

审查通过后必须执行功能测试，不能用审查结论、单元测试、构建成功或接口返回成功替代。

### 1. 自动化检查

- Go 改动执行 `just verify`（`go mod tidy`、`go vet ./...`、`go test ./...`、`go fmt ./...`）。
- 前端改动在 `web/` 下执行 `pnpm typecheck`、`pnpm lint`、`pnpm test`；影响构建、路由或产物时再执行 `pnpm build`。
- 涉及数据库或并发行为时，按改动影响追加相应集成测试或 `go test -race`。
- 检查失败先判定原因；由本次改动导致时修复后重新走审查与功能测试。

### 2. 启动真实环境

- 优先使用 `just run` 启动后端和前端；后端默认 `127.0.0.1:5080`，前端默认 `127.0.0.1:5173`。
- 缺少本地基础设施时按 README 使用 `just dev-init`，不得执行 `just dev-clean` 等会破坏数据的清理命令。
- `/livez`、`/readyz` 或前端可访问仅表示环境就绪，不能作为功能通过依据。
- 记录启动前已有的服务；测试结束后只停止本次启动且不再需要的进程，不干扰用户正在运行的环境。

### 3. 验证后端功能

纯后端或前端未涉及的改动，至少通过实际业务入口完成用户需求对应的流程：

- 验证真实输入、输出和状态转换，而不只检查 HTTP 状态码；
- 核对必要的数据持久化、重新读取结果、失败路径和日志；
- 涉及消息链路时，确认从入口到最终可观察结果的完整路径；
- 外部依赖不满足时明确标记未验证，不得用 mock、单元测试或接口空响应冒充真实功能通过。

### 4. 前后端联调

前端改动、后端改动影响页面行为，或需求包含页面展示时，必须启动前后端并通过真实页面验收：

- 使用当前环境可用的浏览器自动化能力打开对应页面，实际执行用户操作；没有浏览器能力时报告阻塞，不将接口验证视为通过。
- 覆盖目标模块入口、主要内容展示、核心操作、结果反馈和刷新后的状态。
- 检查相关加载、空数据、失败提示，以及浏览器控制台和网络请求中的异常。
- 将页面观察与后端数据、日志相互核对，确认不是只有接口返回成功或页面静态占位。
- 完整模块必须包含前端展示与交互；只调通接口、只断言 DOM 存在或只截取静态页面均不算通过。

### 5. 测试失败闭环

功能测试发现 BUG 后：

1. 确认问题是否由本次改动导致或影响目标功能；
2. 修复问题并补充必要回归测试；
3. 重新执行独立 subagent 审查；
4. 重新执行自动化检查和完整受影响功能流程，包括相关页面联调；
5. 重复直到审查与功能测试全部通过。

不能只重跑失败步骤而跳过复审，也不能在修复后沿用修复前的审查或测试结论。与目标功能无关的既有问题应如实报告，不借机扩大修改范围。

## Git 提交门槛

只有同时满足以下条件才可执行 commit、push、创建 PR 或推送 PR 更新：

- 最后一轮独立审查不存在必须修复的功能问题；
- 所有由审查或功能测试确认的问题均已修复并重新验证；
- 自动化检查、本地功能测试和适用页面联调均通过；
- 没有未说明的未验证项、已知功能回归或被隐藏的失败；
- 最终差异只含当前任务需要的修改，`.review/` 内容未进入暂存区。

审查、修复和测试针对的代码内容发生变化后，已有结论失效，必须重新执行相应审查和测试。同一份未变化内容在 commit 后继续 push 或创建 PR 时，可以复用已通过的审查与测试结果。

## 收尾

完成本次要求的 commit、push 或 PR 推送后，删除对应的 `.review/` 审查文档；目录为空时一并删除。Git 操作失败时保留记录，便于继续处理。

最终汇报实际执行的审查轮次、修复项、自动化检查、功能测试和页面联调结果，以及任何未能验证的内容。
